# 设计规范与实施顺序

本记录约束后续落地，不宣布新的视觉风格已被选定。完整唯一通用规范仍为 [DESIGN.md](DESIGN.md)。

## 不可绕过的规范链路

DESIGN 的设计值和语义依赖 → token 生成与 CSS 变量 → 同一套公共组件 → React / 原生消费者。

- 配色、字体、字号、行高、间距、控件尺寸、圆角、边框、阴影及动效都从规范与公共变量取得。缺少适当变量时先补 DESIGN，再生成、检查、消费；不得添加组件私有视觉硬值或产品补丁绕过。
- 结构常量、编译期断点、运行时真实几何测量仍按 DESIGN 已列出的严格例外执行。不能机械地将每个 CSS 字面值变成新 token，也不能扩大例外来绕过设计检查。
- 风格是成套视觉变量之间的关系，light / dark / system 是明暗选择，两者概念分开。当前正式 ThemeController 只实现明暗模式，没有已发布的风格注册表、profile 或 styleId API。确定样板前不创建新的风格值或切换能力。
- 共享结构、交互、无障碍和业务事实不随风格改变。风格不能改变权限、未知状态、安全恢复、受控事实或提交许可。

## 已批准的阶段顺序

用户最新明确要求从最基础组件逐层完成，不能先在上层页面反复修补。以下顺序替代此前“布局优先”的跨层执行方式；已提交的布局修复继续验收，未闭环表格问题保留，不作为跳过基础门禁的理由。

1. **规范、变量与基础样式**：以DESIGN单一源核对语义token、依赖图、明暗映射、字体资源、基础排版/边框/焦点/状态规则，检查生成与消费一致；不创建未选风格值、密度API或重复源。
2. **基础组件**：按当前正式exports清单逐项检查Button、Input、Label、选择控件及基础surface等。默认、hover、active、selected、focus、disabled、busy和invalid的适用合同分别验收；先修共用根因，再验证React/原生、三明暗模式、宽窄屏与缩放。此层未闭环，不追加上层实现。
3. **合成组件**：在已通过的基础组件之上验证Field/InputGroup、布局、工具栏、DataTable等组合；核真实版本、滚动边界、错误全文、分页固有高度。横向定宽合同变更仍需明确批准，纵向修复不能冒称解决横向留白。
4. **通用业务组件**：最后验证登录、管理员初始化、公共Key与日志等如何组合基础能力。业务权限、未知状态、恢复门禁仍由既有owner维护，不用表现调整改写事实。
5. **公共样板与完整状态验收**：逐层完成后，以登录、列表和任务详情样板供用户选定风格。第一版登录仍居中单框；聊天仅参考。根字号放大与真正浏览器缩放分别取证，覆盖必要错误、键盘、焦点和全部适用状态。
6. **项目统一接入**：采用已核验SHA、同generation的正式包与来源清单，逐项目验实际页面。产品只接公共API和业务状态，不复制公共CSS、评分、恢复锁或认证owner。

## 证据口径

每次交付分别列明通过、失败、跳过和未测。保留源码 SHA、包 generation、真实 CSS 像素与原始截图。构建或测试数量不能取代可读性审查；人工观察也不能证明后端原子性、真实读屏器或未访问的产品页面。
